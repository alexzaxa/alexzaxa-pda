AlexZaxa Solutions

live, in production

A restaurant can run its entire floor on it without ever touching the cloud.

A local-network ordering system — waiter tablets, a dine-in floor plan, phone and delivery orders, kitchen printing, and software that updates itself. It's licensed per install and watched over by an admin dashboard that reports income across every store running it. Some installs stop paying; for those, there's a kill switch that actually works.

  • Admin dashboard with income reporting across every licensed store, built on Supabase
  • Offline-verified license keys, each one bound to the machine that first activates it
  • A real remote kill switch — terminate a store and its install goes dark within a minute

LiteVoice

built, not yet proven

A voice channel that doesn't need everything else Discord comes with.

A lightweight, voice-only alternative: a C# client talking to a relay server running on Ubuntu. No text channels, no bots, no screen share — just a room and the people talking in it. The code is written end to end; it hasn't carried a real call yet, so I'm calling it built rather than finished.

  • C# desktop client paired with a dedicated Ubuntu relay server
  • Next milestone is a real multi-person call, not another unit test

Trading bot

planned, not started

The part I've actually finished is deciding how it's allowed to fail.

A crypto trading bot that starts on paper money and stays there until it earns its way onto a real exchange. Before writing the strategy, I wrote the phased plan and the safety gates — what it's allowed to do, what it isn't, and what has to go right before each phase unlocks the next one. No execution code yet; the constraints came first on purpose.

  • Phased rollout: paper trading first, live trading only after it clears each gate
  • Risk limits and kill conditions specified before any strategy code

Security research

active engagement

Scope first, every time — a program's rules are the only permission that counts.

Enrolled in 1win's official bug bounty program, working inside its published scope and rate limits. There's no feature to point at here, by design — the work is finding real issues in someone else's systems without becoming one.

  • Working under an official program's defined scope and request limits

Skopos

live, in production

The bounty's scope document is the only thing allowed to say yes.

A small request gatekeeper I built for the 1win engagement: every outbound request gets checked against the program's published domains and rate limit before it's allowed to leave. If a target isn't on the list, or the limit's already spent for this second, the request never goes out — it's less to carry in my head than remembering the rules correctly every time.

  • Checks every outbound request against the program's scope before it's sent
  • Enforces the 5 requests/second limit locally, not just by discipline

Kleidi

built, not yet proven

The PDA's license system, with the restaurant software peeled off.

AlexZaxa Solutions issues offline-verified license keys bound to the machine that activates them — that logic used to live inside the PDA codebase alone. Kleidi is the same signing and verification scheme, pulled out into its own small library, so the next thing I license doesn't start from zero. It hasn't licensed anything but the PDA yet.

  • Same offline verification and machine-binding scheme the PDA runs in production
  • Not yet wired into a second product

Fylakas

live, in production

The thing that notices when one of the things above goes quiet.

A small watchman that pings every system on this page that's actually live and tells me the moment one stops answering — a store's PDA going dark, a relay dropping, Skopos itself falling over. It's the least interesting project here, and the one I'd miss first if it broke.

  • Watches every live system on this page, PDA included
  • Alerts on silence, not just on error — a hang looks the same as a crash to it

Anemos

live, in production

Every PDA install updates itself without me touching the restaurant's PC.

The signed-update distributor behind the PDA's self-updating software: packages a release, signs it, and lets every live install pull it down and swap over on its own schedule. It's the kill switch's mirror image — instead of shutting an install down, it's what keeps every one of them current without a site visit.

  • Signs every release before it's allowed to reach an install
  • Runs on the same schedule as the income sync, no separate agent

Dokimi

built, not yet proven

Every strategy loses on history before it's allowed near paper money.

A backtester that replays a trading strategy against real historical price data before the trading bot's paper gate even opens. It's written and it runs end to end — I just haven't fed it a strategy worth trusting yet, so it has nothing to report.

  • Replays historical price data against a strategy before paper trading starts
  • Outputs the same risk metrics the live gates will eventually check

Apothema

planned, not started

The PDA already knows what a store sold today; this would be what it's about to run out of.

An idea more than a project so far: use the order history the PDA already collects to flag ingredients a restaurant is likely to run low on, instead of waiting for the kitchen to notice. It needs real sales data to be worth building — which is exactly what AlexZaxa Solutions has been quietly accumulating.

  • Would read from the same daily-totals data the income dashboard already uses
  • Not started — needs more stores running the PDA first

Nomos

planned, not started

Every project above has its own version of "these are the rules" — this would be the one place they're written down.

The kill switch's conditions, the trading bot's gates, Skopos's scope list — right now each one encodes its own rules separately. Nomos is the idea of pulling them into one format I can read and audit in one place, instead of trusting I wrote the same constraint correctly in four different codebases.

  • Would unify rule-logic already duplicated across the PDA, the trading bot, and Skopos
  • Still just the idea — the duplication it would fix is real and already live

How I tend to work

Ship the whole system, not the demo
The PDA isn't just an app — it's the licensing, the update pipeline, the dashboard that watches it, and the kill switch for when a store stops paying. If I can't operate it after launch, it isn't done.
Fail safe, not silent
A sync job that can lock a restaurant out of its own software only acts on a clear signal — any network error or bad response leaves things exactly as they were, rather than guessing.
Constraints before code
For the trading bot, the paper-first gates got written before a single order-execution line did. For the bug bounty, the scope and rate limit got read before the first request. The rules come first.
