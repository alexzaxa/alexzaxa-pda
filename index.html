AlexZaxa Solutions

A restaurant can run its entire floor on it without ever touching the cloud.

The problem

Most restaurant ordering systems assume a reliable internet connection and a monthly cloud bill a small place can't always justify. Staff need something that works on the Wi-Fi that's already there, keeps running when the internet doesn't, and doesn't need a technician visit for routine updates.

How it works

Waiter tablets, a dine-in floor plan, phone and delivery orders, and kitchen printing all run on the restaurant's local network. An admin dashboard reports income across every licensed store, software updates itself in the background, and a remote kill switch handles installs that stop paying.

  • Admin dashboard with income reporting across every licensed store, built on Supabase
  • Offline-verified license keys, each one bound to the machine that first activates it
  • A real remote kill switch — terminate a store and its install goes dark within a minute
  • Self-updating software — every install signs and pulls its own releases, no site visit

Skopos

live

Σκοπός · the scope

The program's scope document is the only thing allowed to say yes.

A small request gatekeeper built for an active bug bounty engagement: every outbound request gets checked against the program's published scope and rate limit before it's allowed to leave. If a target isn't on the list, or the limit's already spent, the request never goes out.

  • Checks every outbound request against program scope before it's sent
  • Enforces the program's rate limit locally, not just by discipline
12:04:02 → GET api.target.example/v2/users?id=118
12:04:02 ✓ in scope, under limit — sent
12:04:03 → GET not-the-target.example/admin
12:04:03 ✗ not in scope — blocked before it left

Fylakas

live

Φύλακας · the watchman

The thing that notices when something else goes quiet.

A small watchman that pings every live system here and alerts the moment one stops answering — the PDA going dark, Skopos falling over. It watches for silence, not just errors; a hang looks the same as a crash to it.

  • Watches every live system here, PDA included
  • Alerts on silence, not just on error

Anemos

live

Άνεμος · the wind

Every PDA install updates itself without me touching the restaurant's PC.

The signed-update distributor behind the PDA's self-updating software: packages a release, signs it, and lets every live install pull it down on its own schedule. The kill switch's mirror image — this is what keeps installs current instead of shutting them down.

  • Signs every release before it's allowed to reach an install
  • Runs on the same schedule as the income sync, no separate agent

Kleidi

built, not yet proven

Κλειδί · the key

The PDA's license system, with the restaurant software peeled off.

AlexZaxa Solutions issues offline-verified license keys bound to the activating machine — that logic used to live inside the PDA codebase alone. Kleidi is the same scheme pulled into its own small library, so the next thing I license doesn't start from zero. Hasn't licensed anything but the PDA yet.

  • Same offline verification and machine-binding scheme the PDA runs in production
  • Not yet wired into a second product

Δοκιμή · the trial

Every strategy loses on history before it's allowed near paper money.

A backtester that replays a trading strategy against real historical price data before the trading bot's paper gate even opens. Written and runs end to end — I just haven't fed it a strategy worth trusting yet, so it has nothing to report.

Nomos

Νόμος · the rule planned, not started

The kill switch's conditions, the trading bot's gates, Skopos's scope list — each encodes its own rules separately right now. Nomos would pull them into one format to read and audit in one place. Still just the idea; the duplication it would fix is real.

How I tend to work

Ship the whole system, not the demo
The PDA isn't just an app — it's the licensing, the update pipeline, the dashboard that watches it, and the kill switch for when a store stops paying. If I can't operate it after launch, it isn't done.
Fail safe, not silent
A sync job that can lock a restaurant out of its own software only acts on a clear signal — any network error or bad response leaves things exactly as they were, rather than guessing.
Constraints before code
For the trading bot, the paper-first gates got written before a single order-execution line did. For the bug bounty tooling, the scope and rate limit got read before the first request. The rules come first.
